## Warnings (should fix; not blocking)

1. **Stale snapshot pointer can serve old listings labeled as fresh — and is redundant.**
   `internal/ingestion/service.go:239` writes `sanctions:current_snapshot` with **no TTL** after publish, while `internal/sanctions/service.go:204-225` reads it on every lookup. If that post-publish `Set` fails (Redis hiccup), the old version persists *forever*: readers keep resolving `wallet:sanctions:{net}:{addr}:{oldVersion}` cache keys and can serve pre-publish results — including listings revoked in the new snapshot — for up to `lookupCacheTTL` (1h), while `data_status`/`last_synced_at` are recomputed from the *newest* snapshot row (`service.go:57`, `freshness` at `service.go:228-237`). A revoked wallet could read `matched:true` + "fresh" freshness for up to an hour. Separately, the pointer buys nothing: `currentSnapshot` queries `LatestSnapshotPublished` on **every** call anyway (`service.go:207,214`). Fix: drop the Redis pointer and use `snap.Version`, or write the pointer with a TTL and prefer the newer of pointer vs DB version.

2. **Provenance asymmetry: references and entity-program links are hard-deleted on every publish.**
   `queries/ofac_publish.sql:25-29` (`PublishDeleteEntityProgramsForSource`) and `:103-107` (`PublishDeleteReferencesForSource`) wipe all rows for the source and rebuild from staging. Entities and wallet listings are correctly soft-revoked (`revoked_at`, `:79-101`), but a delisted entity's official references and program links vanish permanently — staging is deleted on success (`service.go:246`) and the source XML is removed post-run (`service.go:196`). "Which official reference justified this listing last quarter?" becomes unanswerable for revoked entities, weakening the §6 provenance rule while the rest of the model honors it. Fix: apply the same `revoked_at`/soft-delete pattern to `sanctions_references` and `sanctions_entity_programs`, or document an explicit "current-state projection" decision in the plan and spec — if references are intended as historical provenance, this rises to a critical defect.

3. **`data_status` missing on entity-detail and program-detail responses.**
   `internal/sanctions/handler.go:128-142` returns `last_synced_at` but no `data_status`; `handler.go:163` (program detail) returns neither. The freshness invariant ("every result carries explicit status") is only applied to the wallet lookup path. OpenAPI schemas mirror the gap, so contract and code are consistent — but the domain rule that no result read as context-free is under-applied. Fix: include `data_status` (and `last_synced_at`) on both endpoints.

4. **Contract drift vs spec §9.3 and the phase-05 success criterion.**
   The implemented `sanctions[]` entry omits `list` and returns `source:{code,name,url}`; the spec example and phase doc promise `sanctions[].list` and `source:{provider,record_id,url}` — a criterion phrased as "response keys match spec example contract" is not literally met (`service.go:146-158`, `api/openapi.yaml:473-489`). The implemented shape is arguably better (`external_entity_id` is the honest record id; `source.code` is the provider) and is self-consistent in OpenAPI — but the deviation should be reconciled by amending spec/plan text or the response, not left implicit.

5. **Stale-run sweep marks live long-running ingestions FAILED.**
   `queries/ingestion_runs.sql:29-32` unconditionally sets `status='FAILED'` on any `RUNNING` row older than 1h, called at boot (`service.go:66-70`, `cmd/api/main.go:192`) and inside `begin` (`service.go:145`). There is no liveness check (heartbeat/`updated_at`), so a legitimately >1h run flips to FAILED mid-flight (it self-heals to COMPLETED at `finish`, but operators see a false failure and the RUNNING unique index is released early — the advisory lock still protects correctness). Related: a worker crash leaves the row for up to 1h and blocks re-runs via `uq_ingestion_runs_running` — operationally acceptable but should be documented. Fix: touch a heartbeat during long stages, or reap only when the run is provably dead (e.g. session check), and document the ~1h post-crash gate.
